## Reproduced failure and change

The original strict playback test already passes on the accelerated ARM64
baseline, with 11 ms maximum in its eight initial playback samples. This does
not erase the historical software API 26 x86 failure of 886 ms.

The added recovery suite exposes a separate concrete coordination failure in the
baseline: seeking while already playing can leave both players READY with
`playWhenReady=false`. Repeated-seek and trailing-dub tests time out. The stalled
local-source test passes. The before CSVs preserve command transitions and the
stuck clocks, rather than counting a READY player as successfully playing.

Media3 can defer listener callbacks while another listener event is dispatching.
The old stack-scoped `internalChange` Boolean was already false when the app's
own synchronization-pause callback arrived; that callback cleared
`waitingForDub` as if the user had paused. The fix retains ordered pending
play-state acknowledgements until their callbacks arrive and clears them when
players close. No inference, additional polling, relaxed limit or decoder/thread
change was introduced.

After this change all recovery tests pass: a deliberately blocked local AAC
source freezes the video; multiple seeks during buffering recover to the latest
requested position at 1.25×; repeated playing seeks preserve playback; pause and
original/dub switching keep the clocks aligned; and final audio continues over
the last video frame and reaches its own end.

This fixes the reproduced seek-resume hang. The old software x86 environment has
not been rerun, so its 886 ms failure is not relabeled as fixed or passed.
